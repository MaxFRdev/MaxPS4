# v0.6.0 GPU and Metal compatibility report

Scope: GPU emulation and Metal rendering only (PM4 decoding, GCN shader
translation, textures, render targets, GPU/CPU synchronization). Game startup,
PRX loading, HLE and FEXCore are covered on the Codex branch and are out of
scope here.

Baseline: `main` at 38b28fd. Everything below was found by reading the code and
the existing tests. **No new game has been tested on an iPhone for this
report**, so it claims no compatibility gain. Mortal Kombat Legacy Kollection
and Sonic Mania remain the only titles confirmed on device (60 images/s).

**Update (2026-11-24, `main` at c4d6dfd):** since this report was written,
#339 added stencil, #340 added multiple render targets and #341 reads
1D micro-tiled textures (tile modes 5, 9 and 13). The sections below are
marked where these PRs changed things.

## 1. How a frame is drawn today

1. The guest submits DCBs (`sceGnmSubmitCommandBuffers`). `PS4GnmQueue::submit`
   (`maxps4_ps4_gnm_queue.h`) checks the PM4 framing and passes the words to
   the host consumer (`PM4GameMetalBridge`). It then *retires* the memory
   writes at once: EOP/EOS labels, `RELEASE_MEM`, `WRITE_DATA`.
2. `PM4DrawCollector` (`PM4DrawCollector.hpp`) keeps the context, SH and
   uconfig register banks. It turns each draw packet into a self-contained
   `PM4Draw` and each `DISPATCH_DIRECT` into a `PM4Dispatch`.
3. `PM4MetalRenderer` translates the VS/PS/CS GCN code to MSL
   (`GCNTranslator.hpp` plus the shared runtime `GCNShaderRuntimeShared.inc`),
   keeps colour targets and depth buffers as Metal textures, and writes back to
   guest memory only what the CPU must read.
4. `PM4ResourceScan` runs the GCN interpreter on the CPU to find which buffers
   and images each draw reads before the GPU runs it.

## 2. PM4 packets

Handled by the collector: `SET_CONTEXT_REG` (0x69), `SET_SH_REG` (0x76),
`SET_UCONFIG_REG` (0x79), `CLEAR_STATE` (0x12), `INDEX_TYPE` (0x2a),
`INDEX_BASE` (0x26), `DRAW_INDEX_2` (0x27), `DRAW_INDEX_OFFSET_2` (0x35),
`DRAW_INDEX_AUTO` (0x2d), `DISPATCH_DIRECT` (0x15).
Retired by the queue: `EVENT_WRITE_EOP` (0x47), `EVENT_WRITE_EOS` (0x48),
`RELEASE_MEM` (0x49), `WRITE_DATA` (0x37), and the flip NOP.

Not supported. Every packet in the list below is **dropped silently** (the
collector's `default:` case), so no failure counter shows it:

| Packet | Opcode | Effect when a game uses it |
|---|---|---|
| `DRAW_INDIRECT` | 0x24 | draw lost, nothing reported |
| `DRAW_INDEX_INDIRECT` | 0x25 | draw lost, nothing reported |
| `DRAW_INDEX_INDIRECT_MULTI` / `DRAW_INDIRECT_MULTI` | 0x38 / 0x2c | draws lost (Call of Duty MWR is expected to use these) |
| `DISPATCH_INDIRECT` | 0x16 | compute lost |
| `SET_BASE` | 0x11 | indirect argument base not tracked |
| `NUM_INSTANCES` | 0x2f | instancing ignored: one instance drawn |
| `DMA_DATA` | 0x50 | CP copies and fills never happen |
| `WAIT_REG_MEM` | 0x3c | GPU-side waits ignored (harmless while work is retired at submit) |
| `SET_CONFIG_REG` | 0x68 | ignored |
| Constant engine (CCB): `WRITE_CONST_RAM`, `DUMP_CONST_RAM`, CE counters | 0x81 to 0x86 | on the Metal (host) backend a non-null CCB is **ignored**, not refused (`kind_ < null` guard). Descriptors that Gnmx's CUE dumps from CE RAM are then never written |

Other limits in the collector:

- ~~Colour target 0 only~~. **Done in #340**: MRT 1 to 7 at target 0's size are
  drawn. Those at another size are dropped and counted in the report.
- **Primitive types**: list, fan, strip and rect list only. Points and lines (1,
  2, 3) and quads fail the draw.
- **Scissor**: only `PA_SC_SCREEN_SCISSOR` (0xa00c/0xa00d) is applied. The
  generic, window and viewport scissors (0xa090, 0xa081, 0xa094) are not.
  To check against a game that uses a narrow generic scissor.
- **`CLEAR_STATE`** zeroes the context bank. The hardware loads default values
  instead. To check if a game relies on non-zero defaults.
- **Async compute** (`sceGnmDingDong`): labels and memory writes happen, but the
  dispatches never run (`PS4GnmQueue::compute`).

## 3. GCN shader instructions

The translator refuses an instruction with a precise message
(`unsupported <name> at 0x...`), which shows up in the diagnostic report.
Known refusals:

- **LDS**: only `ds_swizzle_b32` in quad mode. `ds_read*`, `ds_write*`, the LDS
  atomics and GDS are refused: most compute shaders that use groupshared memory
  fail.
- **Depth-compare sampling** (`image_sample_c*`, shadow maps): refused.
- `image_sample_cd*`, `image_gather4*` and `image_get_lod`: refused.
- **Mip levels**: `image_sample_l/_b/_lz` sample level 0. LOD, bias and clamp
  are ignored.
- **1D, 3D, cube and array textures**: the interpreter refuses every type other
  than 2D. The translator samples them as 2D.
- **Buffer stores and image stores** only in compute programs. `addr64`
  buffer access is refused.
- **Exports**: `mrtz` (target 8, depth written by the PS) is refused.
- **Fixed in this branch**: `image_sample_d*` read the derivatives as
  coordinates (see section 9).

## 4. Textures and tiling

- **Linear textures** (tile mode 8): the CPU path decodes dfmt 1, 2, 3, 4, 5, 10,
  11, 12, 14, 16 to 19 and BC1 to BC5. Metal samples 8_8_8_8, 5_6_5 and 8 natively
  through views of guest memory.
- **BC7**: only in tile mode 13. It is detiled and decoded once on the CPU
  (`bc7Texture`).
- **1D micro tiling** (tile modes 5, 9 and 13) is read since #341, on the CPU
  and in Metal shaders, including BC formats.
- **2D macro tilings** (for example 10 and 14) **still read as zero**, unless
  the T# is at the address of a colour target that Metal already holds. This
  remains a likely cause of black or transparent sprites.
- Data formats not decoded: 10_11_11 / 11_11_10 (6, 7), 10_10_10_2 /
  2_10_10_10 (8, 9), 32_32_32 (13), BC6 (40).

## 5. Render targets

`targetFormat` maps 8_8_8_8 (UNORM, SNORM, SRGB, BGRA swap), 16_16_16_16,
16_16, 16 (FLOAT, UNORM, SNORM), and 32, 32_32, 32_32_32_32 FLOAT. Any other
format fails the draw ("colour target format"). The most common missing ones
are **2_10_10_10 / 10_10_10_2** (0x8 / 0x7), **11_11_10** (0x6, HDR scenes), 8
and 8_8 (0x1 / 0x3), and 5_6_5 / 1_5_5_5.

Depth is kept in Metal and never written back to guest memory. **Since #339**
it is `Depth32Float_Stencil8` and stencil is emulated. Operations Metal cannot
express exactly are approximated and counted in the report.

## 6. Synchronization and writeback

- Labels and `WRITE_DATA` are written **when the work is submitted**, before
  Metal runs it. A game that reads a render target from the CPU once its EOP
  label arrives can therefore see the previous contents. The renderer limits
  this with `writebackGuestWrites` (compute stores and targets the CPU reads).
- Colour targets live in Metal textures. A T# at the same address and in the
  same dfmt reads the texture directly (`targetReads`). A T# in another format,
  or a CPU read, goes through writeback.
- A compute shader that writes a tiled image fails the draw explicitly ("tiled
  compute stores are unsupported"). This is good: it is not dropped silently.

## 7. Black-screen causes, by likelihood

1. A 2D macro-tiled texture that is not a render target reads as zero
   (section 4). 1D micro tiling is read since #341.
2. A draw is skipped silently: an indirect draw or `NUM_INSTANCES`
   (section 2).
3. A CCB is ignored on the Metal backend, so descriptor tables stay empty
   (section 2).
4. The colour target format is refused ("colour target format"): visible in
   the report.
5. A shader is refused (LDS, depth compare): visible in the report.
6. Async compute never runs, so a post-process result stays empty.

Points 4 and 5 already show in the diagnostic report. Points 1, 2, 3 and 6 do
not, which makes them the hardest to find from a user report.

## 9. First fix: `image_sample_d` coordinates

In GCN, the address VGPRs of `image_sample_d`, `_d_cl`, `_d_o` and `_d_cl_o`
are laid out as offset, then derivatives (four in 2D: ds/dx, dt/dx, ds/dy,
dt/dy), then coordinates. The interpreter (`GCNInterpreter.hpp`) and the
translator (`GCNTranslator.hpp`) skipped only the offset and the bias, so they
sampled at ds/dx, dt/dx.

Fix: skip four more registers for these four opcodes, in both places.

Tests:

- `GCNInterpreterTest`: the derivatives point at the white texel and the
  coordinates at the green one. The result must be green.
- `GCNTranslatorTest`: the generated MSL must call `gcn_sample(..., gf(v6),
  gf(v7))`.

The change only affects programs that use these opcodes. Neither Mortal Kombat
nor Sonic Mania shaders have shown them in the reports so far. To confirm on
iPhone that nothing changes for these two games.
