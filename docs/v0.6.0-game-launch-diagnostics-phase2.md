# MaxPS4 v0.6.0 — Game launch diagnostics, Phase 2

État au 16 novembre 2026. Travail prévu sur la branche de développement de v0.6.0, en continuité avec la PR #315. Aucun changement n'est destiné à `main`.

## Périmètre

Cette phase améliore l'observabilité du démarrage et des soumissions graphiques. Elle ne tente pas de rendre acceptés les ELF, imports, instructions FEX, paquets PM4 ou shaders actuellement refusés. Aucun jeu tiers ni reproduction sur iPhone n'a été fourni : les causes liées à un titre précis restent à établir.

## Pipeline examiné

`MaxPS4GameSession.run` ouvre le runtime, charge `eboot.bin` et les PRX du dossier, prépare les modules avec `OrbisLinker`/`GuestELF`, puis lance le stub d'initialisation et l'entrée via FEXCore. Les appels libkernel sont servis par le dispatcher HLE; les appels GNM passent par le collecteur PM4 et le renderer Metal; VideoOut suit les tickets de présentation et les VBlank fournis par la session.

## État des diagnostics et changements de cette phase

| Zone | Déjà présent dans le moteur | Complément de cette phase |
|---|---|---|
| Imports et appels HLE | Le rapport compte les imports non résolus **effectivement appelés**, et montre les appels récents et échoués. | Ajout d'un anneau borné séparé des derniers appels HLE réussis; aucun changement de politique de retour, les imports manquants ne sont pas globalement rejetés. |
| Fautes FEX | Le runtime conserve la première faute invitée observée (signal, code, adresse et RIP), y compris une faute d'un thread enfant qui arrête le processus. | La session inclut cette faute dans son rapport final. Aucun changement d'exécution. |
| Chargement ELF/PRX | Les échecs de préparation/lien renvoient un diagnostic. | Les erreurs d'ouverture, lecture et analyse identifient le chemin du fichier et l'étape; les erreurs de montage et d'allocation ont aussi un contexte. Les PRX facultatifs ignorés et les reprises sans eux figurent dans le rapport de session. Tests ajoutés pour `eboot.bin` absent/mal formé et PRX facultatif invalide. |
| Initialisation PRX | Les initialiseurs `DT_INIT` sont appelés avant l'entrée. Un statut négatif arrête déjà le lancement (fix de Phase 1). | Chaque initializer associé à son module rapporte son statut signé, ou « did not return » si l'appel n'atteint pas son retour. Les résultats paraissent dans les rapports live et final. |
| PM4 | Le rapport Metal expose les refus de draw/dispatch, erreurs de shader/pipeline, compteurs et adresses/programmes utiles. | Une erreur de cadrage PM4 précise l'index du dword, l'en-tête et l'opcode fautif; tests pour paquet tronqué, type non pris en charge et limite de paquets. |

Les enregistrements restent bornés (anneaux d'appels existants, premier défaut PM4, une ligne par initializer) et ne tracent pas chaque appel HLE en mode normal.

## Problèmes confirmés et hypothèses

### Confirmés par le code

1. Avant la Phase 1, un `module_start` à statut négatif n'était pas remonté au lanceur. La Phase 1 vérifie le signe, arrête l'entrée du jeu et préserve les statuts non négatifs; les fixtures couvrent les deux cas. Cela établit un défaut du chemin, pas qu'il causait un échec observé dans un jeu donné.
2. Les imports manquants peuvent être appelés et recevoir zéro. Le rapport peut maintenant les identifier sans transformer ce comportement permissif en rejet général.
3. Le parseur et le renderer ne prennent en charge qu'un sous-ensemble de PM4/GCN/Metal; ils savent refuser certaines entrées. Une erreur PM4 de cadrage avait un message trop générique, maintenant localisé.
4. Les compteurs de présentation, l'appel HLE actif et les fautes invitées existent déjà dans des rapports partiels; cette phase les rassemble dans le rapport de fin avec les résultats PRX.

### Hypothèses à valider sur un cas reproductible

- Un import HLE effectivement manquant peut mener à un pointeur invalide, à une initialisation incomplète ou à un écran noir; le nom et l'ordre des derniers appels doivent être comparés au crash réel.
- Un shader GCN, état de draw, format de ressource ou paquet PM4 refusé peut expliquer une image noire/incomplète. Le code du rapport permet de séparer parseur, traduction, pipeline et soumission Metal.
- Un écart entre présentations demandées, tickets affichés et VBlank peut localiser un arrêt dans le jeu, le backend graphique ou la présentation. Ces compteurs seuls ne diagnostiquent pas la cause.
- Les échecs de mapping/mémoire, de format ELF/SELF, d'import ou de relocation doivent être lus depuis l'étape exacte remontée par le loader; aucune correction générale n'est proposée sans reproduction.

## Compatibilité et limites

Les changements ne touchent ni les contrôleurs, ni le multijoueur, ni la politique d'acceptation des imports, ni la traduction GCN/Metal. Le chemin startup vérifié en Phase 1 reste couvert par ses fixtures, y compris le retour positif existant et le statut négatif. Les tests automatisés ne démontrent pas que Mortal Kombat Trilogy ni un autre jeu fonctionne sur appareil; un essai iPhone demeure nécessaire.

## Tests et intégration

Tests de régression ajoutés : chargement d'un exécutable absent/mal formé, diagnostic d'un PRX facultatif invalide, statut retourné par les initialiseurs PRX, appels HLE réussis et position/en-tête des paquets PM4 refusés.

Sur le commit d'implémentation `4decafe4d3fe8d6f4f30cabb712b11f061b5ad56`, les 32 vérifications CI déclenchées par la PR #317 ont passé (0 échec, 0 en attente), notamment le test FEX lié sous simulateur VIXL et ARM64 natif, les tests PM4, services PS4, mémoire ELF, compilation Swift/iOS et liaisons FEXCore iOS/host. La compilation/test local n'a pas été lancé, faute de compilateur C++/Xcode sur l'hôte Windows; la CI GitHub a exécuté les suites disponibles. La revue iOS/Metal dépend de ces jobs macOS; aucune intégration ni fusion dans `main` n'est autorisée par cette tâche.
