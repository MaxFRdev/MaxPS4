# MaxPS4 v0.6.0 — compatibilité des jeux, phase 1

État de l'analyse : 16 novembre 2026, branche `develop/v0.6.0-game-compatibility`, base `main` au commit `38b28fd7c1654f313065de29bd5e7e6aabce3fb5`.

## Portée et limites

Cette revue suit le chemin d'exécution présent dans le code et ses fixtures synthétiques. Aucun nouveau jeu 2D, dossier de jeu reproductible ni rapport d'exécution sur iPhone n'a été fourni pour cette phase. Les causes spécifiques à un jeu restent donc des hypothèses; aucun résultat de test hôte ne prouve qu'un jeu fonctionne sur appareil.

## Chemin actuel de lancement

1. `MaxPS4GameSession.run` ouvre le moteur FEX, renseigne le dossier d'update et appelle `maxps4_fex_engine_load_game`.
2. Le chargeur trouve `eboot.bin`, les PRX de `sce_module/`, les PRX au niveau racine et les remplacements de l'update. Les PRX racine sont facultatifs; les modules `sce_module/` et l'exécutable sont requis. Les modules racine peuvent être ignorés si leur préparation échoue.
3. `OrbisLinker` analyse ELF/SCE, les dépendances, imports NID, symboles, relocations, segments et TLS. Les modules sont liés selon leurs dépendances. Des variantes d'un même module appelées par chemin gardent des exports privés pour `sceKernelDlsym`.
4. `GuestELF::prepare_orbis_general` réserve une plage d'adresses identiques côté invité et hôte, reloge les images dynamiques, copie les segments, prépare TLS, pile, fenêtre `mmap` et stub d'entrée.
5. Le stub appelle les `DT_INIT` des PRX dans l'ordre de dépendance; pour un PRX, ce `DT_INIT` est traité comme `module_start(0, NULL, NULL)`. Il lance ensuite l'entrée du jeu selon l'ABI PS4.
6. FEXCore JIT exécute le code x86-64 invité sur ARM64. Les appels système passent par les services HLE de libkernel; les appels GNM sont remis au renderer Metal.
7. Le chemin graphique décode les paquets PM4, lit l'état et les ressources invitées, traduit le sous-ensemble GCN reconnu en Metal et présente les cibles rendues par VideoOut.

## Problèmes confirmés et priorités

### P1 — Erreur négative de `module_start` ignorée (corrigé dans cette branche)

Avant ce changement, le stub appelait chaque `module_start`, puis continuait vers l'entrée sans examiner `RAX`. Un module qui renvoie une erreur pouvait donc laisser le jeu continuer avec son état partiellement initialisé, donnant un échec plus tardif ou un écran noir difficile à relier à son origine. C'est un défaut démontrable du chemin de démarrage, pas une cause confirmée d'un plantage observé sur un jeu précis.

Le chemin général vérifie maintenant le signe de `EAX`: les valeurs non négatives continuent; une valeur négative termine le processus invité avec ce statut avant l'entrée du jeu. Ce choix conserve le comportement du fixture historique, dont le statut de succès est positif. La fixture FEX couvre un statut négatif et conserve le cas de succès existant. Le chemin borné de démonstration n'est pas le chemin utilisé par les jeux et reste inchangé.

### P1 — Imports non implémentés remplacés par zéro (comportement confirmé; effet jeu à établir)

Le mode de lancement normal active la sonde permissive d'imports. Lorsqu'une fonction importée n'a pas de HLE, le dispatcher enregistre le symbole manquant et renvoie `0` à l'invité. C'est utile pour identifier les appels inconnus, mais ce retour peut ressembler à une réussite; si le jeu appelle ensuite le pointeur nul ou dépend d'un effet non effectué, un crash ou un écran noir peut suivre. Il faut relever les imports effectivement appelés dans le rapport d'un jeu avant de décider d'un refus ciblé. Remplacer ce comportement par un rejet global risquerait de casser le lancement actuel, notamment MK Trilogy.

### P1 — Rendu Metal/GNM limité à un sous-ensemble (limitation confirmée; impact jeu à établir)

- Le parseur refuse les paquets PM4 et opcodes hors de son sous-ensemble. Le renderer peut refuser des états, formats, shaders ou pipelines qu'il ne sait pas traduire.
- La traduction GCN et son interpréteur ne couvrent pas toutes les instructions ou formats. Le chemin interpréteur indique explicitement que les textures échantillonnées doivent être linéaires (tile mode 8); quelques cibles tuilées reconnues par Metal peuvent être utilisées directement, mais cette exception ne couvre pas toutes les ressources.
- Les écritures compute dans les images tuilées et les écritures invitées hors des images visibles sont refusées, car la synchronisation/writeback générale n'est pas implémentée.

Ces refus peuvent expliquer une image absente ou incomplète alors que le thread CPU continue. Le diagnostic Metal distingue draw refusé, shader non traduit et dispatch compute refusé; il faut conserver ce motif exact avec le prochain rapport de jeu.

### P1 — Images protégées ou formats ELF non pris en charge

Le chemin de lancement exige des ELF/PRX en clair dans un dossier accessible. Il n'ouvre pas le contenu chiffré d'un PKG/SELF. En mode d'adressage général, un `ET_SCE_EXEC` à adresses fixes n'est pas relogeable et est refusé; l'image doit être relogeable (`ET_SCE_DYNEXEC`/PRX) pour ce backend. Des tags dynamiques, imports, relocations ou formats de blocs non pris en charge entraînent aussi un refus. Un échec ici survient avant l'entrée du jeu et doit être distingué d'un crash FEX.

### P2 — Réservation et mapping de mémoire sous contraintes iOS

Le backend général doit réserver une plage contiguë avec identité adresse invité/hôte, sous `2^47`, avec place pour les segments, la fenêtre `mmap`, les piles, TLS et les caches FEX par thread. Il essaie plusieurs tailles de fenêtre, de 24 Gio à 1 Gio; un conflit d'adresse ou une capacité insuffisante peut empêcher le chargement avant l'exécution. Le code protège les plages et refuse les chevauchements, les droits W+X et les accès hors segments. Un `compute guest-memory writeback failed` relève plutôt du chemin graphique/synchronisation Metal et ne suffit pas à conclure à un défaut de mapping CPU.

### P2 — PRX préparés au démarrage plutôt que chargés à la demande

Le runtime prépare les PRX racine et `sce_module/` au chargement du jeu; `sceKernelLoadStartModule` retrouve ensuite un handle par nom de fichier. Cela couvre les modules actuellement observés, dont les variantes `libmipsaot` de MK Trilogy, mais n'est pas équivalent à un chargeur qui charge un module au moment de l'appel, lui fournit ses arguments et traite individuellement son statut. Un jeu 2D qui dépend de modules tardifs, de chemins particuliers, d'arguments de démarrage ou de dépendances dynamiques non préchargées pourrait échouer. Aucun cas concret supplémentaire n'a été reproduit.

## Causes possibles à départager avec des rapports

| Symptôme | Causes étayées par le code | État |
|---|---|---|
| Lancement refusé avant le premier thread | ELF/PRX protégé, dépendance/NID/relocation inconnue, format dynamique non pris en charge, réservation d'adresses refusée | Limites confirmées; il faut le diagnostic du jeu pour choisir laquelle |
| Crash au début | instruction x86 non traduite par FEX, HLE manquant renvoyant zéro, pointeur invité invalide, module initialisateur en erreur | Mécanismes confirmés; attribution à un jeu non vérifiée |
| Écran noir avec CPU actif | PM4/registre/primitive non géré, GCN ou texture refusés, état de pipeline Metal absent, format/cible non reconnu | Hypothèses à valider par le compte-rendu PM4/Metal |
| Image figée après une première présentation | soumission GNM/Metal bloquée, writeback invité refusé, cible/ticket VideoOut absent | À reproduire avec timestamps de soumission, draw/compute et tickets VideoOut |

## Préserver Mortal Kombat Trilogy

Cette correction ne modifie ni les contrôles, ni l'ordonnancement multijoueur, ni les chemins de rendu. Le test de démarrage réussi reste dans `PS4FEXLinkedExecutionTest`; le nouveau cas couvre un résultat négatif de `module_start`. Le support hybride deux joueurs de PR #313 reste couvert par `ControllerSlotsTest`, `PS4PadTest` et les tests de session/entrée du workflow. Ces tests ne remplacent pas un essai sur iPhone avec MK Trilogy.

## Suite proposée

1. Garder le contrôle de retour de `module_start` et ajouter une ligne de statut au rapport de fin afin que les erreurs de démarrage soient immédiatement visibles.
2. Pour chaque nouveau jeu 2D, collecter son diagnostic de préflight, les imports manquants effectivement appelés, les derniers appels HLE, le premier PC fautif, le motif de refus GCN/PM4 et les compteurs VideoOut.
3. Ajouter un fixture ciblé pour chaque refus ou bug reproduit; ne pas élargir les refus d'imports ou les formats Metal sur la seule base d'une hypothèse.
4. Tester l'IPA sur iPhone avec MK Trilogy en solo puis en mode hybride avant toute intégration. Les tests hôte/CI ne démontrent pas la compatibilité réelle d'un jeu.

## Tests de cette branche

La régression synthétique de `module_start` est ajoutée; elle vérifie qu'un statut négatif arrête l'entrée du jeu tout en conservant le cas de démarrage réussi existant (statut positif). Les résultats du runner CI et du workflow iOS seront consignés avant la PR. Aucun test sur appareil n'a été effectué dans cette phase.
